# Product Experience Principles

## 1. Substance before ceremony

A developer should reach a project, specification, schema, example, or source repository faster than an institutional biography.

## 2. One ecosystem, many independent projects

The website should make projects feel related without pretending they share one release number or maturity level.

## 3. Status everywhere it matters

Status appears on:

- project cards;
- project pages;
- documentation headers;
- search results;
- RFC references;
- release notes;
- schema downloads.

Status is conveyed by label and text, never color alone.

## 4. Public pages explain; docs enable

The public site answers “why, who, and what.” Documentation answers “how, exactly, and under what requirements.” Avoid duplicating full technical content in marketing pages.

## 5. Progressive technical depth

Each project should offer a path:

1. plain-language overview;
2. quick example;
3. implementation guide;
4. reference;
5. normative specification;
6. source and tests.

## 6. Source is visible but not required

GitHub is important, but users should not need to browse repository trees to understand a standard. Every documentation page may link to source and editing controls.

## 7. Search is navigation

The global search interface should understand concepts, exact fields, project aliases, RFC numbers, and page headings. It is not merely a full-text input in the header.

## 8. Documentation is a product

Treat docs as a maintained application with:

- information architecture;
- versioning;
- usability tests;
- error states;
- performance budgets;
- analytics;
- accessibility;
- release ownership.

## 9. Texture supports identity, not legibility

Paper and linen textures should remain subtle. Long-form reading surfaces stay visually quiet.

## 10. Honest incompleteness

A well-designed “Planned” or “Experimental” page is better than invented stability. Clearly state what exists, what is proposed, and what is not implemented.

## 11. URLs are durable public infrastructure

Routes for specifications, versions, RFCs, and decisions should be designed as citation targets. Redirects must be retained indefinitely when routes change.

## 12. No account wall

Everything in this phase is public. Search, downloads, docs, source links, feeds, and newsletters must not require an account.
