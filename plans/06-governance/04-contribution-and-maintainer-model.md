# Contribution and Maintainer Model

## Contribution channels

- GitHub Issues for concrete defects and scoped requests
- GitHub Discussions for early ideas and questions
- Pull requests for reviewed changes
- RFCs for material proposals
- Security contact for vulnerabilities
- Foundation contact for governance or conduct concerns

## Contribution types

Recognize:

- code;
- specification text;
- educational scenarios;
- schema review;
- examples;
- test fixtures;
- accessibility;
- security;
- privacy;
- internationalization;
- research;
- documentation;
- design;
- community support.

## Pull-request expectations

A contribution should include, when relevant:

- problem and rationale;
- affected project/version;
- normative impact;
- examples;
- tests;
- docs;
- compatibility notes;
- security/privacy impact;
- linked issue or RFC.

## Contributor license approach

Prefer Developer Certificate of Origin sign-off over a broad copyright assignment unless future legal review identifies a need for a CLA.

Example:

```text
Signed-off-by: Name <email>
```

Document what sign-off means and provide automation.

## Maintainer criteria

A maintainer should demonstrate:

- sustained, constructive contributions;
- sound judgment within project scope;
- respect for governance and code of conduct;
- timely review and communication;
- ability to distinguish implementation preference from normative need;
- willingness to disclose conflicts;
- understanding of security, compatibility, and documentation obligations.

## Nomination

1. Existing maintainer or founder nominates.
2. Candidate confirms interest and disclosures.
3. Public feedback period.
4. Founder appoints during initial phase.
5. Appointment decision is recorded.

## Maintainer scope

Appointments are scoped:

- project maintainer;
- documentation maintainer;
- tooling maintainer;
- governance maintainer;
- security contact.

Avoid granting broad organization rights when narrow permissions suffice.

## Inactivity

A maintainer may move to Emeritus after an agreed period without participation. Security-sensitive access should be removed promptly even when public recognition remains.

## Removal

Grounds may include:

- sustained inactivity;
- repeated policy violations;
- undisclosed conflicts;
- security negligence;
- abuse of authority;
- request by the maintainer.

Material removals receive a private due-process step and a public record appropriate to privacy and safety.

## Contributor recognition

Generate contributor summaries from Git history only as a starting point. Permit recognition for non-Git contributions through a maintained registry.
