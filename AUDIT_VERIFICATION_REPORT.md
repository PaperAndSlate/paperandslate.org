Date: 2026-08-27  
Status: local release-candidate audit complete; not production-ready  
Scope: current workspace, the pasted master implementation prompt, and the plan pack under `plans/`

This is the current verification record. It supersedes older historical receipts in `IMPLEMENTATION_REPORT.md`, `LAUNCH_READINESS.md`, and `EXTERNAL_ACTIVATION.md` for current status. ## Decision

The implementation is substantial and the local source/build gates are mostly healthy, but it is not fully implemented or ready for release. The following must be resolved before a staging acceptance claim:

1. Production JavaScript currently fails under the strict CSP. A production Lighthouse browser run recorded blocked inline scripts and React hydration error `#412`; development CSP allowances hide this in the normal Playwright run.
2. Six documentation project links return 404. They are generated by the project registry/navigation and are reachable from public pages.
3. The Lighthouse and container evidence wrappers do not run under the repository's current `tsx` CommonJS configuration. The Lighthouse wrapper also assumes an output directory that the failed/manual run did not populate and starts the wrong server mode for a standalone build.
4. The visual snapshots are development-server captures containing the Next development indicator and a visible issue overlay. The screenshot harness also logs a hydration warning caused by its caret-hiding mutation. They are not clean release evidence.
5. The generated requirements ledger is materially stale: successful local checks remain marked `not-started`, many plan headings are represented by generic traceability rows, and the ledger therefore cannot prove substantive completion.
6. External authority, qualified approvals, provider activation, immutable release identity, production deployment, monitoring, rollback, and publication acceptance are still absent by design.

The current tree does contain earlier accessibility corrections for a contrast issue and a missing project-record heading; the rerun of the RC axe suite passed. That is useful audit evidence, not evidence that every planned accessibility surface has been reviewed.

## Findings and resolution plans

The plans below are deliberately not executed in this audit.

### AUDIT-001 — Production CSP breaks hydration and interactivity (P0 for release)

Evidence: `apps/web/src/proxy.ts` emits production `script-src 'self'` without a nonce or hash. The manual production browser report is under `.lighthouseci/lhr-1787827160202.json` and records two CSP violations plus React error `#412`. It also records a failed `label-content-name-mismatch` audit.

Resolution plan:

1. Choose and document a Next-compatible strict policy: request-scoped nonce propagation, or a reviewed hash/static-script strategy. Keep production free of `unsafe-eval`; do not treat development allowances as production evidence.
2. Exercise the actual standalone production server in a browser with JavaScript enabled. Fail the check on CSP violations, hydration/runtime errors, failed chunk loads, or nonfunctional search/theme/mobile controls.
3. Extend `security:check` so it validates the effective response/browser behavior in addition to source text.
4. Re-run smoke, axe, visual, Lighthouse, link, and feed checks against the same production artifact.

Acceptance: zero CSP violations and React/runtime console errors on all representative production routes, with search, theme, navigation, forms, and documentation actions still interactive.

### AUDIT-002 — Six generated documentation project roots return 404 (P0/P1)

Evidence: `pnpm links` found these internal failures:

- `/docs/paper-and-slate`
- `/docs/well-known-discovery`
- `/docs/organization-schema`
- `/docs/curriculum-standards-schema`
- `/docs/course-catalog-schema`
- `/docs/tools-and-libraries`

The links originate in `packages/content/src/registry.ts`, `apps/web/src/components/docs-navigation.tsx`, `apps/web/src/components/docs-project-selector.tsx`, and the documentation breadcrumb. The current dynamic page resolves document leaves but has no project-root landing document. This conflicts with the requested `/docs/[project-slug]` surface.

Resolution plan:

1. Add a real project-root/index document route for every ingested project, selecting a deterministic current/next landing page and exposing version choices.
2. Make navigation, selector, breadcrumb, sitemap, canonical metadata, and raw-document links use the same route resolver rather than independently concatenating strings.
3. Add dynamic project roots to the route manifest and assert every public internal link, sitemap URL, canonical URL, and redirect target resolves.
4. Re-run the BFS link test and add a regression test for every current project slug.

Acceptance: no public internal 4xx/5xx links, project roots render useful content, and all generated route inventories agree.

### AUDIT-003 — Lighthouse/container evidence wrappers are not executable (P1)

Evidence: `scripts/lighthouse.ts` and `scripts/container-check.ts` contain top-level `await` and fail under the current CommonJS `tsx` execution. `scripts/lighthouse.ts` launches `next start` even though the build uses `output: standalone`; Next warns that this mode is unsupported. `lighthouserc.json` writes to `.generated/launch/lighthouse`, while the interrupted manual LHCI run wrote to `.lighthouseci`. Windows Chrome temporary-directory cleanup also raised `EPERM`.

Resolution plan:

1. Wrap each script in an explicit async `main()` with deterministic error handling and an exit code suitable for CI.
2. Start the supported standalone server from `.next/standalone` when that artifact is selected; verify `/health` and the exact build identity before auditing.
3. Use one configured Lighthouse output directory, clean it at the start of a run, and make `performance:check` consume that directory.
4. Configure or isolate Lighthouse temporary profiles so Windows cleanup cannot turn a completed report into a false failure; preserve the HTML/JSON report on failure.
5. Run all configured routes and runs, then test the wrapper on an intentionally failing fixture.

Acceptance: `pnpm lighthouse`, `pnpm performance:check`, and `pnpm container:check` each run end-to-end on Windows and CI, with retained reports and truthful nonzero failures.

### AUDIT-004 — Performance budget enforcement is incomplete (P1)

Evidence: `config/performance-budgets.yml` defines JavaScript, CSS, image, request-count, and Lighthouse thresholds. `scripts/performance-check.ts` currently checks category scores, LCP, CLS, and TBT only; it does not enforce the resource-size or request-count budgets.

Resolution plan:

1. Parse Lighthouse network/resource summary data for transferred JavaScript, CSS, images, fonts, and request count.
2. Define whether each budget applies per route, per run, or to the release maximum, and record that policy.
3. Fail with route, resource class, actual, budget, and report path when a budget is exceeded.
4. Add fixtures for pass, one-resource-over-budget, and aggregate-over-budget cases.
5. Reassess the observed approximately 91 KiB unused-JavaScript opportunity and the client bundle boundaries after correctness is restored.

Acceptance: every budget in the YAML is enforced by an automated report tied to the release artifact.

### AUDIT-005 — Best-practice and accessibility naming defect (P1)

Evidence: the production diagnostic scored best practices 0.93. Lighthouse identified the search trigger's visible text (`Search ⌘/Ctrl K`) as not matching its accessible name (`Open search`).

Resolution plan:

1. Choose one coherent accessible-name contract: include the visible label in the name, or separate/hide the shortcut text according to the approved accessibility pattern.
2. Add a browser assertion for visible text/name consistency and retain the existing keyboard focus tests.
3. Re-run Lighthouse and axe on the production artifact, including the compact/mobile header.

Acceptance: the label-content-name-mismatch audit is clean and keyboard/screen-reader users receive the same action meaning as sighted users.

### AUDIT-006 — Visual gate is development-only and baseline approval is incomplete (P1)

Evidence: six RC snapshots exist under `tests/browser/snapshots/`, but they were captured with the development server. The images show the Next development indicator and a light-mode `1 Issue` overlay. Playwright logs a hydration mismatch associated with its screenshot-time caret-color mutation on inputs. Existing legacy homepage snapshots remain historical and were not replaced.

Resolution plan:

1. Capture the route/state matrix from `docs/visual-evidence-plan.md` against the clean standalone production artifact with dev tooling disabled.
2. Wait for hydration and font/media readiness before capture; eliminate or isolate screenshot-harness mutations that create false hydration diffs.
3. Compare current captures with the supplied references and record approved deviations rather than silently updating baselines.
4. Obtain owner visual approval and media-rights approval for each published asset.
5. Make the release gate invoke the intended RC suite explicitly and keep legacy snapshots as a separately named historical comparison if they remain useful.

Acceptance: clean production screenshots, retained diffs, zero unexplained differences, and an approval record for every intentional deviation.

### AUDIT-007 — Traceability ledger overstates plan completion (P1)

Evidence: `.generated/requirements/requirements.json` reports 1,030 `implemented`, 9 `partial`, 8 `blocked-external`, and 19 `not-started` records. Several core rows remain `not-started` despite passing local checks (for example formatting, lint, SBOM, secret scan, and RC visual/a11y work), while 1,018 generated plan rows use the generic wording “represented in the generated requirement ledger.” The mechanical check therefore passes without providing substantive acceptance for each plan section.

Resolution plan:

1. Reconcile all 48 `WEB-REQ` rows against the current code and command evidence, correcting status, file references, tests, and evidence paths.
2. Split “implemented locally,” “verified locally,” “blocked by owner/external state,” and “not started” where one status currently conflates them.
3. Replace generic plan rows with explicit links to the substantive requirement or mark them as traceability-only in a separate report.
4. Add a stale-status check that fails when a recorded passing command has no corresponding implemented/verified evidence or when an implemented item has no test/evidence path.
5. Regenerate `IMPLEMENTATION_LEDGER.md` and have the release owner review the remaining partial/blocked rows.

Acceptance: the ledger is an auditable map from each plan requirement to implementation, test, evidence, and owner/external blocker, without implying that a heading mirror is completion.

### AUDIT-008 — Documentation rendering and route coverage need a single contract (P1)

Evidence: central reviewed documents use Fumadocs rendering, while other documents are compiled at request/build time with `@mdx-js/mdx` and then wrapped in `DocsBody`. Project-root links are missing, and `routes:check` does not cover the dynamic route set.

Resolution plan:

1. Define the supported document model, renderer, component allowlist, source/provenance rules, version/index behavior, and raw route behavior in one contract.
2. Ensure central and non-central content receive equivalent heading, code, link, image, table, metadata, and error handling.
3. Generate route/index manifests from the same normalized document data used by the page and navigation.
4. Add tests for current, historical, alias, raw, project-root, missing, and malformed documents.

Acceptance: every normalized document has one canonical route, valid aliases, a useful project root, safe rendering, and matching route/navigation/sitemap output.

### AUDIT-009 — Newsletter abuse controls are process-local and under-tested (P1)

Evidence: `apps/web/src/lib/newsletter.ts` uses in-memory maps for rate limiting fallback and idempotency. `allowedOrigin()` accepts requests with no `Origin`; the API uses the first untrusted `x-forwarded-for` value as the abuse key; and `content-length` does not cap a chunked request body. No provider delivery/credential/consent round-trip is proven.

Resolution plan:

1. Decide the production proxy trust model and derive client identity only from sanitized trusted headers or a platform primitive.
2. Require an approved same-origin/CSRF policy for browser submissions, including behavior for absent or malformed origins.
3. Enforce a bounded request body independent of `content-length` and test JSON/form/chunked/oversized inputs.
4. Move idempotency and rate-limit state to the approved distributed service with TTLs, or explicitly document a single-instance limitation and launch restriction.
5. Add Kit sandbox tests, delivery/duplicate/failure assertions, consent retention evidence, and secret-leak checks without recording secret values.

Acceptance: abuse controls remain correct across replicas and restarts, request bodies are bounded, and provider behavior matches the approved privacy/consent policy.

### AUDIT-010 — Time-dependent publication and sitemap filtering are unsafe (P1)

Evidence: `packages/content/src/news.ts` hardcodes `item.date <= "2026-08-26"`. `apps/web/src/app/sitemap.ts` includes every release record, although the current records are `unreleased`/`planned`.

Resolution plan:

1. Inject a supplied publication clock/timezone or use an explicit reviewed cutoff policy; test future-dated, scheduled, corrected, superseded, and archived content.
2. Define which release states are public and filter sitemap, search, feeds, pages, and AI-readable outputs consistently.
3. Resolve every generated sitemap URL in the route/link test and assert no draft/unreleased record leaks.

Acceptance: publication is deterministic for tests, safe around dates/timezones, and only approved public records appear in public discovery surfaces.

### AUDIT-011 — Local release/security evidence is not yet release identity (P1)

Evidence: local SBOM and scans exist, but there is no committed source SHA, signed tag, immutable image digest, registry receipt, SLSA/in-toto-style provenance, or clean-environment verification. Development-tool advisories remain open.

Resolution plan:

1. Establish the canonical repository and protected release branch with owner approval.
2. Build from a reviewed commit, record lockfile/build/tool versions, and publish an immutable image digest.
3. Generate CycloneDX and SPDX SBOMs for the lockfile and final image; attach digests and scan summaries.
4. Sign the artifact/attestation using the approved keyless or managed-key policy and verify it from a clean environment.
5. Record advisory disposition, exceptions, remediation owner, and expiry before staging promotion.

Acceptance: the deployed artifact, source commit, signed tag, image digest, SBOM, provenance, and vulnerability decision form one verifiable release identity.

### AUDIT-012 — Historical reports contain stale claims (P1 documentation quality)

Evidence: the older reports still refer to T031/T038/T044/T104–T130, an old middleware path, prior page counts, and Lighthouse/Docker states that do not match the current tree. `scripts/launch-report.ts` also emits historical receipts rather than the current audit result.

Resolution plan:

1. Keep historical receipts immutable but label them as historical and link to this report.
2. Update the launch/evidence generator to consume current command results, current paths, and current release identity.
3. Generate one current summary from the reconciled ledger and evidence bundle; do not hand-edit generated tables.

Acceptance: a reviewer can identify the current source of truth and every claim has a current command/report or an explicit owner blocker.
